# Historical V1 features, resources and limitations

> This records the original M0–M8 build. Current source uses ABI 0 revision 6; use BUILDING.md and CONFIGURATION.md for current compatibility. Measurements below are not measurements of the current base.

V1 is the completed M0–M8 prototype scope, with experimental C ABI 0 revision 3. It is a trusted-native-code development runtime, not a memory-protected production OS. See [M8 evidence](milestones/M8.md) and [reproduction commands](BUILDING.md).

## Supported features

| Capability | V1 support |
| --- | --- |
| Hosts | macOS ARM64; Linux ARM64 and x86-64 |
| MCU | Adafruit ESP32 Feather V2, ESP32-PICO-V3-02, 8 MiB flash |
| Source languages | C17 and freestanding C++17 through the same C ABI |
| Native placement | Four device fixed slots; restricted host Mach-O/ELF64 |
| Lifecycle | Serialized hooks/timer callbacks, admission, cleanup, callback quiescence, timeout recovery |
| Resources | Bounded arenas/stacks/handles/timers, exclusive logical GPIO ownership |
| Hardware demo | Real button publisher, independent protobuf logger, onboard red LED subscriber, C++ fourth service |
| IPC | Local stream/latest, copied bounded messages, independent cursors, explicit loss |
| Packages | Immutable versions, image/schema hashes, declared interface compatibility, graph admission |
| Local management | Install/list/configure/plan/activate/boot/status/logs/start/stop/restart |
| Network management | Pinned TLS identity, bearer authorization, image/graph transfer, activation, status/logs/stop/reboot |
| Recovery | Two service banks, committed journal, two trials, five-second liveness, base-owned fallback and physical recovery |
| Persistent service data | Version zero only; no migration or service storage API |

The network controller is a privileged service linked into the base. Its operation set excludes arbitrary flash and base updates. This API restriction does not prevent arbitrary trusted native code from accessing physical resources outside the API.

## Device measurements

Measured on the network-enabled final base with four independent services. The V1 suite uses a 50 ms button sample timer, a 64-byte protobuf stream with depth eight, logger/LED subscribers, and the C++ cooperative worker. TLS is enabled; these lifecycle measurements do not generate concurrent remote requests.

The C++ image uses 164 code bytes, 132 initialized-data bytes, no BSS, and a four-byte arena. Four Running services reported stack headroom of 2944, 2872, 2788 and 3312 bytes at the first post-confirmation observation. A post-reboot logger observation reached 2784 bytes. This is measured headroom for this workload, not a general stack safety proof.

The diagnostic latency sample contained 159 publication-to-logger observations: minimum 277 µs, median 1802 µs, maximum 3383 µs. Samples span the short lifecycle/reload experiment; they are not a worst-case deadline bound. Earlier three-service measurements and method are retained in M5.

Static linker sections, reserved slots, heap snapshots, runtime accounting and host file bytes describe different memory classes and must not be summed as independent RAM consumption. Wi-Fi/TLS allocates additional transient heap; the M7/M8 remote reports show live snapshots during actual requests. No full peak-allocation trace or PSRAM budget is claimed. Static IRAM has only about 4 KiB remaining, so further base features require measurement and likely memory tuning.

## Bounded limits and recovery

The graph supports at most four resident services and four channels. Channel depth is at most eight and payloads at most 256 bytes; the board demo uses one depth-eight, 64-byte channel. Device aggregate worker stacks are 16 KiB. Each native slot admits up to 8 KiB code and 4 KiB initialized data/BSS. The host rounds worker stacks to at least 64 KiB and the OS minimum (128 KiB on the tested Linux ARM64 system).

The device has two 128 KiB banks in its raw service partition and two 4 KiB journal sectors. One current good graph is protected while the other bank is staged. Starting a new update may reuse the older retained bank; arbitrary package history belongs in the developer's package store. The host store permits 64 packages within 64 MiB, independently of the four-service residency bound.

Two durably counted attempts and five seconds of Running/progress status qualify a candidate. A hung service causes runtime/device recovery rather than unsafe memory reclamation. Holding the user button during reset enters the physical base controller without executing service hooks. Software reset injection passes all twelve write/commit/boot boundaries; analog brownouts and flash wear endurance have not been qualified.

## Explicit exclusions

No MMU/MPU isolation, adversarial native-code sandbox, arbitrary relocation loader, general C++ standard library, event channels, distributed IPC bridge, general SPI/I2C driver suite, Bluetooth service transport, service-data migrations, signed-package authority, kernel OTA or redundant recovery firmware is delivered. Updates have staging downtime. The TLS endpoint is for a trusted development LAN; provisioning and identity rotation require physical access. Keep generated firmware private because it embeds credentials.
