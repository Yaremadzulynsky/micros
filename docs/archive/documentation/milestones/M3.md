# M3 — Bounded Protobuf IPC

Status: Complete on the host; ESP32 base/service builds remain regression targets. The full graph moves to hardware in M5.

## Implemented contract

- Four configured channels maximum, each with at most eight slots and 256 encoded bytes per slot. The payload pool has a fixed 8,192-byte physical capacity; configuration reports its admitted payload reservations separately from fixed kernel metadata.
- `stream` retains ordered history. Every subscription owns its next sequence. A lagging reader receives `MICROS_ERROR_MESSAGES_MISSED`, the count lost, and the oldest retained sequence, with zero payload bytes. Its cursor advances to that oldest message; retry reads it.
- `latest` uses depth one. Each subscriber receives the newest unread value; skipped samples are reported in metadata without treating deliberate coalescing as a stream error.
- Reads and publication are synchronous, bounded copies under the runtime lock. Multiple publishers serialize in lock-acquisition order. Readers never observe a partially overwritten message, and their progress cannot block publication indefinitely. Publish success means the bytes were retained, not that anyone processed them.
- Empty reads are explicit. Insufficient output capacity reports the required bytes and preserves the cursor. Oversized publication leaves the channel unchanged. Caller buffers are not retained.
- New stream subscriptions begin at the oldest retained message; new latest subscriptions begin at the current newest value. Channels survive individual service restarts until the controller destroys them.
- Publisher/subscriber handles consume the service's admitted handle quota and validate owner, resource type, and channel generation. Channel recreation invalidates old references, while close still releases those stale registrations. Generation exhaustion retires channel slots. The final sequence value is reserved so cursor advancement never wraps.
- Timer and GPIO ownership rules remain unchanged. IPC acquisitions/publication are suppressed during stop; cleanup releases registrations.

The native API is experimental ABI 0 revision **3**. Four IPC callbacks are appended to the revision-2 table. The image envelope and native descriptor layouts remain unchanged, and old revisions are rejected. M1 host/MCU harnesses expose explicit unsupported IPC callbacks.

## Protobuf SDK and demo

The checked-in `Sample` schema lives with the sensor-pipeline example. A small allocation-free C codec implements that scalar proto3 schema, with defaults, uint32/uint64 varints, sint32 ZigZag, duplicate-field last-value semantics, and bounded unknown-field skipping. It rejects truncated/overflowing input and leaves decoded output unchanged on failure. Deprecated groups are explicitly unsupported. This is a dedicated codec, not a general protobuf compiler/runtime. Its implementation follows the [official wire-format specification](https://protobuf.dev/programming-guides/encoding/), with interoperability checked against Google's Python protobuf implementation.

Three independently built service images form the demo: one 10 Hz synthetic publisher, a fast logger, and a deliberately delayed logger. `demo.samples` is a fixture key mapped to a depth-eight, 64-byte stream. Both consumers decode protobuf independently. The delayed reader pauses for 1.2 seconds, reports lost messages, and resumes without affecting the fast reader. The two-second run stops/unloads all three and destroys the channel, returning services, handles, channels, reservations, and worker tasks to zero.

The three-service run exposed a desktop descheduling interval beyond M1's inherited 10 ms work threshold. The host manager now uses a 100 ms step/callback failure threshold; init/start/stop remain one second. This is host failure detection, not an MCU real-time guarantee. The ESP32 M1 harness retains its separate 10 ms step policy.

## Validation

Eleven CTest entries include the M1/M2 suites plus:

- Stream/latest boundaries, two independent cursors, explicit loss, capacity without cursor advance, empty messages, owner rejection, channel recreation, and forced sequence/generation exhaustion.
- Twenty thousand concurrent publications with two readers through the synchronized SDK path; every received payload matches its sequence with no torn bytes.
- Thirty-six edge/random scalar messages compared byte-for-byte and decoded against Google's protobuf implementation, plus unknown/duplicate fields and malformed input.
- Twenty thousand bounded malformed-input trials, extreme scalar values, output-buffer capacity, and no mutation on decode failure.
- The independently loaded three-service demo, requiring fast-reader progress, slow-reader loss and recovery, and a clean resource baseline.

The full suite also passes with kernel/BSP/codec ASan and UBSan instrumentation. Reproduction commands are in [BUILDING](../BUILDING.md); evidence is in [evidence/m3](evidence/m3).

No package admission, persistent channel configuration, channel permissions derived from manifests, or reliable `event` policy is claimed here. Those belong to M4 and later milestones. The kernel treats payloads as opaque; protobuf validation is the receiver's responsibility.
