# M6 — Transactional Activation and Base-Owned Recovery

Status: Complete.

## Storage and commit protocol

M6 replaces the M5 development SPIFFS service store with raw bounded service banks. This avoids relying on filesystem recovery when a candidate write is interrupted. [Espressif documents SPIFFS corruption risk during interrupted operations](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32s2/api-reference/storage/spiffs.html). Partition-relative APIs constrain every write to the service or activation partition; no activation operation writes base firmware, NVS or bootloader.

The service partition contains two 128 KiB banks. Each bank has one 4 KiB graph sector and four 16 KiB native-image regions; the remainder is reserved. The active known-good bank cannot be written. Candidate transfers are bounded and validated before flash writes; the whole bank is hashed from flash before selection. The SHA-256 identity includes the complete graph and every referenced image in graph order. Native descriptors and admitted budgets are independently checked before any graph hook.

Two separate 4 KiB activation sectors contain alternating 132-byte records. Each records a strictly increasing sequence, good/previous/candidate bank identifiers and SHA-256 identities, trial count, CRC, and a final commit marker. Updating a selection erases only the alternate sector, writes its payload/CRC, then programs the commit marker last. Boot chooses the highest complete valid sequence. Exhaustion is rejected rather than wrapping. The existing complete selection remains available at every earlier write boundary.

Each candidate gets at most two boot trials, durably counted before native code executes. Five seconds in Running state with successful results and completed cooperative steps establishes prototype liveness. It does not prove application correctness. A failed or hung candidate cannot mark itself healthy; the base controller commits confirmation or selects fallback. Reverting service code cannot access migrated persistent state: package persistent-data version must remain zero and the ABI exposes no persistent-data service API.

The last good graph becomes the retained previous graph after successful confirmation. Starting another update can reuse that older bank while protecting the current good graph. Two banks support one candidate plus one good graph; arbitrary version history remains in the developer's immutable package store. MCU transfers currently stop the running graph, so updates have explicit downtime; interrupted staging preserves the selected graph for reconstruction at reboot.

## Host behavior

`microsctl configure` stages the desired selection. After shutdown, `microsctl activate` durably records a trial and boots it. The controller consumes attempts before starting the native process, verifies five seconds of liveness, and commits the good selection. Failed candidates fall back to the retained good selection. Retries preserve the attempt count. `status` reports activation state separately from the desired enablement selection.

Installed immutable packages are retained independently of residency and share the M4 64-package/64 MiB storage bound. Derived images may be regenerated from retained packages. Host records use synchronized temporary files, atomic rename and directory synchronization. The fault suite exercises interruption before and after synchronization/rename; it assumes the host filesystem and device honor those durability operations.

## Physical recovery

Hold the Feather V2 user button (GPIO38) while resetting or reconnecting USB. The base starts the serial controller without entering service code. Release the button. Inspect `STATUS`, stage a valid inactive bank, then issue the physical-development `RESUME` command and activate it. A corrupted selected bank also enters recovery instead of executing unverified content.

A physically flashed base remains the recovery authority; there is no second remote-updatable firmware image. When replacing the base changes fixed slot addresses, rebuild every native service against the new ELF. The M5-to-M6 storage transition requires redeploying the service graph; M5 SPIFFS selections are not migrated silently.

The `FAULT n` development command injects a whole-device reset at one named write/boot boundary and is not exposed through remote management. It never erases or programs outside the same bounded service-store/journal operations. The committed hardware suite must distinguish these reset injections from actual unplugged-power tests; resets test selection logic and interrupted writes, not analog brownout behavior.

## Validation

The shared C journal test exercises all 133 byte-prefix program cuts, all 133 byte-prefix erase cuts, corruption in each record byte, consumed attempts and sequence exhaustion. Host native tests cover successful health confirmation, failed-start fallback, process restart after exhausted trials, idempotent staging and six filesystem commit-boundary interruptions.

The hardware suite in `tests/hardware/activation.py` passed resets at twelve boundaries: inactive image erase/partial write/complete write; graph erase/write; journal erase/partial payload/complete payload/commit; persisted attempt; entered graph; and health confirmation. It also deploys a separately linked failed-start image and verifies automatic fallback after two trials. All twelve cases selected the expected complete graph. The failed-start candidate consumed two trials and selected the prior good bank automatically. The committed transcript and report are under `evidence/m6`. These were on-device software resets at instrumented write boundaries, not analog power-disconnection tests.

All 16 host checks pass with and without ASan/UBSan. The hardware booted and confirmed its first transaction, retained a previous graph through successful swaps, and ended running the original healthy three-service graph after failed-candidate rollback.
