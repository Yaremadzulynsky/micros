# M1 — Independent Native Loading

Status: Complete, 2026-09-05. Independent native loading was demonstrated on macOS arm64 and the connected ESP32-PICO-V3-02.

## Implemented

- A shared bounded image-envelope validator and experimental format 1.
- A macOS arm64 loader with serialized hooks on a managed thread, per-hook deadlines, safe join/unload, and two fresh cycles per invocation.
- An ESP-IDF v5.5.2 serial harness with reserved executable/data slots, direct validated descriptor lookup, and a static core-1 service task.
- Independent freestanding C service builds for two variants, mutable initialized globals, BSS, arena state, and injected SDK calls.
- Local RAM transfer and host/hardware rejection suites.

The image strategy and limits are recorded in [ADR 0004](../architecture/decisions/0004-m1-fixed-slot-loader.md) and the [native image contract](../architecture/native-image.md). Reproduction commands live in [BUILDING](../BUILDING.md).

## Build Evidence

SDK checkout: ESP-IDF v5.5.2, commit `30aaf64524299d3bde422ca9a2848090d1bc5d0f`. Compiler: Espressif GCC 14.2.0, `esp-14.2.0_20251107`. The MCU adapter uses GNU17 for ESP-IDF headers; standalone services use C17.

The initial example uses 280 code bytes, 148 initialized-data bytes, 4 BSS bytes, and a 16-byte arena. It requests a 4096-byte stack. The linked ELF has no undefined symbols or runtime relocations. Object relocations include `R_XTENSA_32` and `R_XTENSA_SLOT0_OP`; disassembly confirms windowed-ABI calls.

The base image reserves 16 KiB of code capacity, 8 KiB of data/BSS capacity, a 4 KiB arena, a 4 KiB service stack, and 24,640 bytes of transfer staging. The UART driver allocates a 32 KiB receive buffer in addition to its bookkeeping. These capacities are harness costs, not actual example payload usage.

The ESP-IDF size report for the built harness reports 67,003 bytes of IRAM and 52,076 bytes of static DRAM, including reserved slots and platform code/state. These figures are link-time usage, not complete runtime allocation totals. The firmware binary is 163,840 bytes; bootloader and partition table are separate.

Host tests exercise both service variants across two load/unload cycles each, eleven invalid envelopes/native layouts, and a stuck hook that exits the runtime. Host image bytes are native file size; OS loader mappings are not fully accounted as MCU-style bounded allocations.

## Hardware Execution Evidence

The [recorded serial output](evidence/m1/hardware.txt) demonstrates both v1 and v2 transferred independently over serial, with two successful lifecycle cycles each. No base firmware rebuild or flash occurred between variants. Each init reported restored initialized globals, zeroed BSS, and a zeroed arena; each stop observed exactly three steps.

Eleven invalid images were rejected: target, ABI revision, section length, descriptor offset, slot address, reserved field, checksum, truncation, arena budget, arena alignment, and null hook. RUN after a rejected load also failed explicitly. The host suite rejects eleven malformed/incompatible images and verifies whole-process recovery for an uncooperative hook.

The [service build report](evidence/m1/service-build.json) records compiler flags and linked section sizes. Stack high-water observations describe this example only, not a safe stack bound for arbitrary services. IRAM/static DRAM size reporting includes reserved capacities; runtime heap excludes those already-reserved static regions. PSRAM is unused and unmeasured. The harness runs at the default configured 160 MHz, while the chip reports 240 MHz capability.

## Device Backup and Current State

The device now boots the M1 serial harness; no service runs continuously after the test cycles finish. The original 8 MiB flash was saved before flashing. The first read was followed by a normal reboot, after which two NVS sectors changed. A second consistent snapshot was assembled while held in the bootloader and verified against the device's full-flash MD5 digest before flashing.

- Verified backup: `build/backups/pre-m1-stable.bin` (8,388,608 bytes, local and ignored by Git).
- Verification details: `build/backups/stable-verification.json`.
- Earlier raw snapshot: `build/backups/pre-m1-flash.bin`.
- Changed sectors after reboot: `0xb000` and `0xc000`, inside the original NVS partition.
- Backup SHA-256: `75a8899aab1d14f221028ca10c99b628fae58e26e73d6c9d38d230f70320ec63`.

The harness bootloader, application, and partition table were flashed at 115200 baud and verified by esptool. A faster initial backup read failed from serial corruption; all accepted backup/flash operations used 115200 baud. The serial client retries its idempotent INFO handshake because opening the USB adapter can reset the board.

To restore the verified original flash, use the activated SDK environment and explicitly run this from the repository root (this replaces the M1 harness):

```sh
python -m esptool --chip esp32 --port /dev/cu.usbserial-564E0535011 \
  --baud 115200 write_flash --flash_mode keep --flash_freq keep --flash_size keep \
  0 build/backups/pre-m1-stable.bin
```

## Scope Carried Forward

One fixed slot, RAM-only transfer, trusted code, macOS-only executable host profile, and a minimal two-function SDK. The final package format, multiple simultaneous services, general resource ownership, IPC, peripheral teardown, persistent activation, and authentication remain later milestones. A new base-image slot layout requires relinking service images. No generic relocation implementation is claimed.
