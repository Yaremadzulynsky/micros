# M8 — V1 Release Validation

Status: Complete. M0–M8 roadmap gates are satisfied for the scope in [V1 features and limits](../V1.md). Product V1 retains experimental ABI 0 revision 3.

## Delivered

The shared host runtime now supports Linux ARM64 and x86-64 with restricted ELF64 native images, platform-specific target identities and monotonic POSIX condition waits. Host stack admission includes the OS runtime minimum: Linux ARM64 required 128 KiB on this system, above the 64 KiB policy used by macOS ARM64/Linux x86-64. Linux libraries are freestanding and reject constructors, dependencies, TLS and resolver behavior before native loading.

The independently linked C++17 example uses the same C ABI with placement construction, cooperative steps and explicit destruction. It runs on all host profiles and in ESP32 slot 3. The hardware graph combines this C++ service with the three independently built C button/logger/LED packages. This demonstrates a freestanding language subset, not an unrestricted C++ runtime.

`tools/release/demo.py` exercises the public CLI through package installation, healthy activation, explicit IPC loss, stop/start/restart, a genuinely different C++ package replacement, failed-update rollback and good-selection reconstruction. `tools/release/build_device.py` builds the base plus all independent hardware validation artifacts without flashing. `tools/release/linux.sh` runs the Linux checks/demo in an isolated tool container. The [build guide](../BUILDING.md), [SDK quickstart](../SDK.md), root architecture and native-image contract now describe the implemented V1; original proposals are marked as historical context.

The ELF parser test covers every truncated length of a valid minimal fixture, forbidden dynamic tags, wrong target, writable executable loads, TLS and 10,000 deterministic mutations under sanitizers. Real compiler-produced constructor, TLS, unresolved import and IFUNC libraries are rejected on Linux. A source-only copy of the candidate checkout was built with empty output directories and no provisioning files. It used the separately installed pinned SDK and Python prerequisites. ## Real hardware results

The network-enabled final base ran all four services. Five cooperative stop/restart cycles returned the stopped heap to 144452 bytes each in the measurement run. All four workers reported Running/success, and reboot reconstructed the confirmed graph with the C++ service. Its native image is 164 bytes code, 132 bytes initialized data and zero BSS; it uses a four-byte arena and 4 KiB worker stack.

The final firmware also passed all twelve M6 reset boundaries and failed-start rollback. The M7 Wi-Fi suite passed unauthorized/oversized/mismatched-hash rejection, unprovisioned TLS rejection, incomplete-transfer preservation, independent LED update, safe stop retry and failed-candidate rollback. The real TLS test ran from local Docker to the physical ESP32 because direct macOS networking returned a routing error.

After those suites, the four-service graph was restored and tested again. All five final stopped-heap observations were 144440 bytes and reboot restored all four Running services. The small difference from the earlier absolute heap baseline reflects separate network startup sessions; each repeated-cycle run remained stable. The board is left running the button publisher, protobuf logger, onboard LED consumer and C++ service.

The [resource report](../V1.md) separates linker reservations, actual image payloads, arena/stack/kernel/channel accounting, and runtime heap snapshots. The base fits with 4041 bytes of static IRAM headroom. That is a concrete growth constraint. Hardware reset injection does not substitute for analog brownout qualification, and measured latency/headroom do not establish worst-case timing or arbitrary-service safety.
