# M5 — Feather ESP32 V2 Service Runtime

Status: Complete.

## Board and services

The user's photograph identifies the Adafruit ESP32 Feather V2 carrier; serial identification confirms ESP32-PICO-V3-02 revision 3.0 and 8 MiB flash. The [manufacturer pinout](https://learn.adafruit.com/adafruit-esp32-feather-v2/pinouts) maps the red active-high LED to GPIO13 and the input-only user button to GPIO38. The BSP exposes these as logical lines 0 and 1. GPIO38 uses the board's external pull-up. GPIO0/2 NeoPixel circuitry and externally connected header pins are outside this profile.

`platforms/esp32/runtime` is the full runtime application. The separate `archive/esp32-m1` M1 loader harness remains an early experiment. The same shared lifecycle, resource ownership, timers and IPC implementation now runs on POSIX and FreeRTOS. Workers serialize hooks and timer callbacks; a higher-priority supervisor enforces deadlines. Shutdown waits for a task to park before deleting its stack, resources and image claim. Unsafe shutdown retains live memory until whole-device reset.

Three independently linked packages form the hardware demo: button reader/publisher, protobuf logger and LED subscriber. The button service samples at 10 Hz. The LED blinks at 1 Hz, holds on while the button is pressed, and reads back each GPIO output level. The logger reports publish-to-decode delay. All three are built from the same service source used by the host GPIO simulation test. No service code is linked into the base firmware.

## Bounds and memory classes

The board reserves four 8 KiB executable IRAM slots and four 4 KiB data/BSS slots. Code copying uses aligned word stores; slot addresses and hook ranges are validated before execution. Independently built images are tied to a specific base ELF and slot. A base firmware relayout requires rebuilding the service images; ordinary service changes require only serial package deployment.

Service arenas, stacks, handles and channels use the shared admission rules, with 16 KiB aggregate worker stacks and only two board GPIO lines. PSRAM is disabled and contributes no assumed capacity. One 4 KiB supervisor stack is accounted separately. The controller has a 12 KiB stack and a 32 KiB UART receive buffer. A transient image buffer is bounded by 64-byte envelope + 8 KiB code + 4 KiB data. Filesystem buffering and RTOS metadata are base-system costs, not hidden service arena usage.

The 8 MiB flash layout contains NVS, PHY initialization, a 1.5 MiB physical-update-only base application, a 4 MiB service-storage partition, and two reserved 4 KiB activation sectors. M5 uses SPIFFS image banks and a development boot selection. First-use formatting can take approximately 90 seconds. M5 does not claim interruption-safe replacement; that is M6's gate.

## Reproduce

Activate the pinned ESP-IDF v5.5.2 environment and install `tools/requirements-dev.txt` into `build/python` as described in the root README. From the repository root:

```sh
idf.py -C platforms/esp32/runtime -B "$PWD/build/esp32-runtime" \
  -D SDKCONFIG="$PWD/build/esp32-runtime/sdkconfig" build
build/python/bin/python tools/packaging/device_demo.py
idf.py -C platforms/esp32/runtime -B "$PWD/build/esp32-runtime" \
  -p /dev/cu.usbserial-564E0535011 -b 115200 flash
build/python/bin/python tests/hardware/runtime.py --port /dev/cu.usbserial-564E0535011
```

The serial port is the observed local adapter name. The hardware suite transfers services, runs two warm-up and three checked stop/reload cycles, verifies stable post-stop heap and both LED output levels, rejects a corrupt image and conflicting slots, and verifies selected-graph reconstruction after reboot. It leaves the demo running. `tools/cli/micros_device.py --port PORT status` shows diagnostics; `stop` turns off the LED and releases the graph.

## Validation and measured limits

Measurements are recorded under `evidence/m5`. GPIO readback establishes electrical output state, not an independent optical measurement. Publish-to-decode timing includes the scheduler and UART logging load at 115200 baud and is not a general hard-real-time guarantee. Button press behavior is implemented; an unattended run validates the observed unpressed input level, without claiming a human pressed the button.

Fourteen host CTest entries pass, including the identical hardware-service sources
on simulated GPIO, with and without ASan/UBSan on the kernel/BSP/codec. The real
board passes five complete cycles, corrupted-image rejection, conflicting-slot
rejection, and reboot reconstruction. Both LED levels are verified electrically.

| Base DRAM data/BSS including four reserved data slots | 27,756 bytes |

| Three service arenas | 120 bytes |
| Three worker stacks / separate supervisor stack | 12,288 / 4,096 bytes |
| Runtime-reported kernel/platform metadata | 13,388 bytes |

The first two cycles retain 264 bytes of base-library bookkeeping; subsequent
three teardowns return to the identical measured heap baseline. This is reported
separately from service resources. Linker archive costs (including FreeRTOS,
SPIFFS, UART and GPIO drivers) are in `evidence/m5/base-components.json`. The
fixed four-slot reservation is paid even when only three images are loaded;
actual service payload must not be added again to that reserved IRAM/DRAM.
